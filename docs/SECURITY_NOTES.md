# SQL ID Library Security Notes

## What This Library Does

This library maps a positive SQL integer ID to a public hex handle and back
again:

```text
SQL integer + label -> layout pack with keyed tag -> secret-keyed Feistel permutation -> lowercase hex
```

The public handle is always 64 bits / 16 hex characters.

The plaintext packed value is:

```text
[ version ][ label ][ zero-based SQL id index ][ keyed validation tag ]
```

It hides sequential IDs and rejects almost all random or tampered strings. It is
not an authorization layer and not a bearer-token system.

## Fixed 64-Bit Layout

| Field   | Bits | Values                                      |
| ------- | ---: | ------------------------------------------- |
| Version |    3 | `0..7`; issues `2`; `1`, `3..6` inactive/future; `0`, `7` reserved |
| Label   |    5 | `0` none, `1..30` named labels, `31` reserved |
| SQL ID  |   32 | public SQL IDs `1..4,294,967,295`           |
| Tag     |   24 | keyed validation tag                        |
| Total   |   64 | 16 hex characters                           |

Label `0` belongs only to the unlabeled API:

```python
id_to_hex(id_value)
hex_to_id(public_hex)
```

Labels `1..30` belong only to the labeled API:

```python
id_to_hex_label(id_value, label)
hex_to_id_label(public_hex, label)
```

Label `31` is reserved and rejected.

## Enforcement Rule

Integer-returning APIs enforce one exact expected label:

```text
hex_to_id(public_hex)                 expects label 0
hex_to_id_label(public_hex, "users")  expects the users label
```

This means:

```text
unlabeled ID -> hex_to_id_label(..., "users") -> None
users ID     -> hex_to_id(...)                -> None
users ID     -> hex_to_id_label(..., "plans") -> None
```

The keyed tag includes the label bits, so a public ID for one label cannot be
retagged or reinterpreted as another label without the secret.

## Secret and Domain Separation

The v3 key schedule combines three independent inputs:

- `DOMAIN_SALT_HEX` near the top of `sql_id_library.py`
- `XCTX_ID_PASSWORD` from the process environment
- the disk pepper file configured by `pepper_file_location`

`DOMAIN_SALT_HEX` is a public-ID deployment hardening value. The bundled salt
is public and accepted by the library, but deployed applications should replace
it with a deployment-specific 32-byte random hex value:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Do not treat the salt as a substitute for the runtime secret or pepper.

`XCTX_ID_PASSWORD` must be a separate value of at least 32 UTF-8 bytes and
should also be generated by the OS CSPRNG:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

The pepper file must contain `64..256` hex characters and defaults to:

```text
~/.sql_hex_id_pepper_file.key
```

Minimum setup:

```bash
python -c "import secrets; print(secrets.token_hex(32))" > ~/.sql_hex_id_pepper_file.key
chmod 0400 ~/.sql_hex_id_pepper_file.key
```

On POSIX systems, the library opens pepper files without following symlinks and
then validates and reads through that same file descriptor. It rejects pepper
files that allow execution, group write, or any other-user access. The
application process must still be able to read the file.

Changing `DOMAIN_SALT_HEX`, `XCTX_ID_PASSWORD`, or the pepper after public IDs
have been issued makes those existing public IDs stop decoding.

The HMAC key schedule includes the layout identity:

```text
scheme revision
version bits
label bits
id bits
tag bits
total bits
hex chars
issue version
reserved label/version policy
pepper bytes
```

The tag HMAC includes:

```text
scheme/layout domain
version
label id
zero-based SQL id index
```

## Random Guessing Profile

For strict exact-label decoding:

```text
valid public IDs = 2^32 - 1
public space     = 2^64
random-valid p   = (2^32 - 1) / 2^64
```

So the probability is just under:

```text
2^-32
```

This applies to both:

```text
label 0 via hex_to_id()
one expected named label via hex_to_id_label()
```

Generic inspection helpers accept any non-reserved label `0..30`:

```python
inspect_hex(public_hex)
hex_to_parts(public_hex)
```

Those helpers are useful for diagnostics, but their acceptance surface is about
31 times wider than an exact-label decoder. Do not use generic inspection as
typed route enforcement.

## Error Ordering

After inverting the Feistel permutation, validation checks the keyed tag before
reporting inactive versions, reserved labels, label mismatches, or ID range
failures.

That keeps malformed random inputs from becoming a useful plaintext-field oracle
except in the rare case where the compact tag is already valid.

## Rate-Limit Hardening

A deployment can make online guessing impractical by treating bad public IDs as
suspicious. Suggested policy:

```text
10 bad public IDs per session/IP/account bucket per 30 minutes,
then a 30-minute block or challenge.
```

This caps guesses to:

```text
10 * 2 * 24 * 365 = 175,200 guesses/year/bucket
```

Strict expected-label expected time to hit any decoder-valid public ID:

```text
2^32 / 175,200 ~= 24,515 years/bucket
```

If the attacker must hit a real row, use:

```text
expected guesses ~= 2^64 / live_row_count
```

for one exact expected label, then still apply normal authorization.

## Intended Use

Suitable:

- compact public SQL-ID obfuscation
- internal public handles
- deterministic row handles where normal authorization is still checked
- route/table/type separation with explicit labels

Not suitable:

- bearer tokens
- reset links
- magic-login links
- invite tokens
- download grants
- API keys
- sessions

For bearer-token uses, generate independent random tokens of at least 128 bits.

## Operational Notes

- Generation returns lowercase hex.
- Decoding accepts uppercase or lowercase hex.
- `id_to_hex()` and `hex_to_id()` return `None` on failure.
- `id_to_hex_label()` and `hex_to_id_label()` return `None` on failure.
- `validate_hex()` validates only label `0`.
- `validate_hex_label()` validates only one expected label.
- `inspect_hex()` returns diagnostic metadata for any non-reserved label.
- `configure_sql_id()` validates the pepper path and/or full local label registry before atomically replacing configured values.
- `load_sql_id_config_from_file()` automatically reuses cached `.json`, `.yaml`, or `.yml` config mappings after the first successful load for a same-stem path.
- Encoding and decoding use the in-memory config path and label registry; normal ID operations read and cache the configured pepper file but do not read config files.
- Cached file loads and config installs are protected by the same lock.
- `reload_sql_id_config_from_file()` explicitly re-reads files and refreshes the cache.
- `reload_sql_id_pepper()` explicitly re-reads the currently configured pepper file and clears derived key-material cache.
- Pepper file permission and symlink checks are performed when the pepper is loaded or explicitly reloaded.
- YAML loading requires optional PyYAML; unavailable YAML support raises `ValueError`.
- Same-stem `.json`, `.yaml`, and `.yml` files are cross-checked and must match exactly after normalization.
- Config files larger than 2000 bytes are rejected.
- Duplicate JSON/YAML keys, duplicate normalized names, duplicate IDs, boolean label IDs, and YAML boolean keys are rejected.
- Missing, unreadable, malformed, low-diversity, overlong, underlong, or unsafe-permission pepper files fail closed.
- SQL ID `0` is always invalid.
- Accepted SQL IDs are `1..(2^32 - 1)`.
- The raw all-ones ID-index state is rejected.
